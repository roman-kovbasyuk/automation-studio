# Финальная чистка и документация дизайн-системы

Дата: 16 сентября 2026. Статус: проект спецификации для утверждения.

**Сейчас разрешены исследование и подготовка спецификации. Изменение кода, удаление файлов, объединение веток и коммиты реализации начинаются только после явного утверждения пользователем.**

## 1. Результат

В репозитории остаётся одна актуальная дизайн-система и одна документация к ней. Устаревшие реализации, демонстрационные экраны, стили и инструкции удалены после переноса ещё нужных зависимостей. Внешнее приложение использует документированный JSON-интерфейс автоматических изменений и получает проверенный пакет.

Готовность означает: актуальный код собран в `main`, проверки пройдены, пакет установлен и проверен в независимом приложении, документация соответствует поведению, изменения закоммичены. Локальные данные Observatory, очереди изменений и настройки машины не входят в продуктовый коммит.

Работа сохраняет текущий дизайн, публичные API и правила Atomic Design. Новый визуальный дизайн, переименование всех компонентов, новые продуктовые возможности и публикация в npm не входят в задачу.

Перед реализацией необходимо повторно снять состояние: другая задача ещё ведёт аудит отдельных копируемых вариантов компонентов. Её незавершённость нельзя считать подтверждением готовности всех примеров.

## 3. Выбранный подход

Рекомендуется **объединить актуальные состояния, затем удалить устаревшее по явному списку**. Сначала сохранить незакоммиченные изменения и свести новую библиотеку с последним протоколом. Затем перенести зависимости старого каталога, переключить документацию и удалить каталог. Такой порядок позволяет проверить каждый этап и восстановить конкретное изменение из Git.

Рассмотренные альтернативы:

- Чистить только `main`: проще, но новая документация и часть компонентов останутся за пределами результата.
- Заменить `main` содержимым `docs-basics`: быстрее, но потеряются более свежие исправления восстановления и выпуска пакетов.

Техническая основа интеграции — отдельная ветка с префиксом `codex/`, созданная от актуального `main`. Незакоммиченные изменения сначала получают проверяемые контрольные снимки. Нельзя применять массовые `reset`, `clean` или удаление рабочей копии с несохранённой работой. Снимки включают нужные новые файлы, но исключают зависимости, секреты, локальные данные и внешние цели символических ссылок.

Компонент не признаётся устаревшим по возрасту, имени, отсутствию в боковой навигации или сходству с другим компонентом. Основание удаления — подтверждённая замена и отсутствие нужного публичного контракта, импортов, примеров и тестового покрытия. Сейчас таких оснований для удаления какого-либо из 66 публичных компонентов не установлено. Tag, Badge, StatusBadge, Tabs и SegmentedControl сохраняются.

Доатомарные `src/components/design-system`, `src/screens` и `src/styles` уже удалены из отслеживаемого дерева `main`. Их наличие в старой рабочей копии не означает, что их нужно повторно переносить в итоговую ветку.

Отдельный список удаляемых файлов составляется перед удалением на основе этой таблицы и проверяется через импорты, входы сборки, публичные экспорты и ссылки. Генерируемые каталоги сборки пересоздаются из исходников; удаление `node_modules` не является частью продуктовой чистки.

## 5. Архитектура и переход на документацию

Направление зависимостей сохраняется: Basics → Components → UI Blocks → Screens. Блоки собираются из Basics и Components; повторно используемые controls принадлежат Components. Новая навигация использует существующие компоненты.

Реестр `src/atomic/componentManifest.js` содержит только метаданные: имя публичного компонента и его актуальный адрес документации. Он не импортирует UI. Проверки сопоставляют реестр с фактическими экспортами, страницами и независимым consumer; фиксированное число 66 не становится вечным ограничением.

Перед удалением каталога необходимо:

1. Переключить `scripts/atomic/verify-consumer.mjs` и `component-docs.test.tsx` на новый путь реестра.
2. Заменить интеграционный тест старого каталога в `panel.test.tsx` проверкой соответствующего поведения текущей документации. Сохранить тесты самого Panel.
3. Проверить, что новая реализация иконок и копирования покрывает нужные сценарии перед удалением старых IconExplorer и copy-mode тестов.
4. Удалить ссылки и тексты, предлагающие старый каталог, включая устаревшее пояснение в BasicsDocs.
5. Обновить входы сборки, правила границ и инструкции: каталог больше не является продуктовым слоем.

Маршруты:

- `/` — Getting Started с установкой и явными ссылками на Basics, Components и UI Blocks. Сейчас таких ссылок на главной странице нет.
- `/basics.html?basic=…`, `/components.html?component=…`, `/ui-blocks.html?block=…` — canonical documentation routes.
- `/getting-started.html` — canonical Getting Started route.
- `/page-20.html` through `/page-23.html` — compatibility redirects for previously documented addresses.
- `atomic.html` — небольшой переход: известные старые якоря ведут на соответствующую новую страницу; неизвестные — на Getting Started. Таблица соответствий строится из существующих якорей каталога до удаления.

Алиасы компонентов должны разрешаться в реальную страницу. Записи `aliases` в навигации сами по себе не обеспечивают обработку URL. Публичный API компонента и алиас страницы — разные сущности.

Руководство по выбору компонентов сейчас импортируется через `?raw` в `usageGuidance.ts` и влияет на отображаемую документацию. Его перенос требует обновления runtime-импорта, парсера при необходимости и проверок соответствия страниц. Датированное имя не делает этот файл архивом. Служебные инструкции из его раздела handoff отделяются от пользовательских рекомендаций.

Каждая страница должна правильно показывать назначение, установку/импорт, реальные props, поддерживаемые состояния, композицию и ограничения. Копирование полного примера возвращает TSX-модуль с импортами, данными, состоянием и обработчиками, необходимыми для показанного поведения. Короткие фрагменты допустимы как явно подписанные пояснения, но не как якобы готовые к запуску примеры. Preview и копируемый пример показывают один и тот же вариант.

Проверка исходников примеров сейчас охватывает только 8 Basics-модулей. Итоговая проверка включает также копируемые примеры Components и UI Blocks и использует публичный пакет, без импортов внутреннего `src/atomic` из приложения-потребителя.

Документация не обещает несуществующие возможности. Например, текущие CommandMenu и DigitInput нельзя описывать как полноценные реализации клавиатурного command palette и OTP-ввода, пока соответствующее поведение не реализовано. Аналогично проверяются fallback Avatar, семантика TabMenuVertical и ProgressRing. Эта работа уточняет документацию и устраняет регрессии перехода; расширение возможностей компонентов оформляется отдельно.

## 7. Протокол внешних изменений

Остаётся существующая локальная модель: одно доверенное npm-приложение, автоматическое одобрение по `single-app-policy`, очередь на диске и worker. Дополнительного шага ручного approve для его запросов нет. Утверждение этой спецификации — отдельное согласование текущей чистки репозитория.

### Интерфейс

Внешнее приложение запускает CLI как subprocess. Для машинного обмена документация использует прямой вызов Node, чтобы служебный вывод npm не смешивался с JSON:

```sh
node scripts/changes/cli.mjs configure --app /absolute/path/to/app --check typecheck --check build
node scripts/changes/cli.mjs request --input /absolute/path/to/request.json
node scripts/changes/cli.mjs get app-change-184
npm run changes:worker
```

Путь приложения и имена проверок — реальные значения выбранного приложения. Worker запускается отдельно и должен работать для обработки очереди. Это CLI-протокол, HTTP API не добавляется.

Вход содержит ровно четыре поля:

```json
{
  "requestId": "app-change-184",
  "installedVersion": "0.1.0-atomic.0",
  "component": "SearchField",
  "change": "Add an optional keyboard shortcut hint."
}
```

`requestId` — 1–80 символов, латинские буквы, цифры, `_`, `-`, первый символ — буква или цифра. `installedVersion` и `component` — непустые строки до 100 символов; `change` — до 4000. Значения обрезаются по краям; лишние поля отклоняются. Повтор одинакового нормализованного запроса возвращает ту же запись; другой запрос с тем же ID вызывает конфликт.

Успешный CLI-вызов выводит JSON в stdout. Ошибка команды выводится в stderr с ненулевым кодом завершения. Публичные статусы:

| Поле/статус | Значение |
| --- | --- |
| `working` | Запрос принят, ожидает worker или выполняется |
| `ready` | Изменение вошло в master, проверенный пакет доступен; возвращаются `version`, `packagePath`, `summary` |
| `failed` | Выполнение, проверка, продвижение или выпуск завершились ошибкой; возвращается `error` |
| `adoption.status` | Отдельный результат обновления приложения: `pending`, `installed` или `failed` |

`ready` не равен успешной установке в приложение. Полный успешный цикл заканчивается `ready` вместе с `adoption.status: installed`. Ошибка приложения не отменяет уже выпущенный пакет.

### Обработка и сохранение данных

Worker создаёт отдельную рабочую копию, выполняет ограниченный запрос, проверяет результат, продвигает его в чистый `main`, сохраняет неизменяемый tarball с уникальной версией и SHA-512. Приложение устанавливает именно этот архив без lifecycle scripts и выполняет настроенные проверки.

При неудаче установки или проверки восстанавливаются прежние `package.json` и `package-lock.json` и их зависимости. Конкурентные изменения этих файлов не затираются: возвращается конфликт с сохранённым журналом. Документация описывает диагностические коды, остановку worker, восстановление после сбоя и расположение журналов. Артефакты, на которые ссылаются lockfiles приложений, нельзя удалять вместе с временными сборками.

Предусловия: чистый `main`, чистые dependency-файлы приложения, совпадающая установленная версия, доступный аутентифицированный Codex CLI и зависимости. Протокол не публикует npm-пакет, не делает remote push и не разворачивает приложение в production.

### Согласование с чисткой

Сейчас worker допускает `fixtures/atomic/**`, тогда как реальный consumer находится в `fixtures/atomic-consumer/**`. Он также не допускает изменение канонического документа usage. После утверждения спецификации разрешённый список должен включить точный consumer-путь и `docs/guides/component-usage.md` для сопровождения изменения компонента. Ограничение фиксируется в prompt и проверках worker; произвольное изменение документации, зависимостей, release tooling и инфраструктуры не разрешается.

В регрессионных тестах нужны разрешённые и запрещённые пути, а также полный цикл принятия, выпуска, установки и отката в синтетическом приложении. Реальный вызов Codex и синтетический adapter описываются как разные уровни проверки.

## 8. Приёмка после реализации

1. **Состав.** В текущем дереве нет старого каталога и его CSS/тестов, кроме предусмотренного перехода. Нет импортов из удалённых путей, битых локальных ссылок или ссылок на `.worktrees`. Сохранены актуальные экспорты и типы.
2. **Границы.** Проверка слоёв и её тесты проходят; перенос реестра не создаёт обратных UI-зависимостей.
3. **Библиотека.** Компонентные тесты, TypeScript, сборки документации и библиотеки проходят. Предупреждение Toggle разобрано; ошибки не скрываются подавлением вывода.
4. **Пакет.** Tarball устанавливается с отдельными зависимостями в чистое временное приложение. Все актуальные компоненты и блоки покрыты; TypeScript, клиентская и серверная сборки и проверка рендера проходят. Symlink на исходный workspace не заменяет эту проверку.
5. **Документация.** Все адреса и заявленные алиасы открываются; с `/` доступны три раздела. Работают поиск, мобильная навигация, копирование и переходы старых якорей. Все полные копируемые примеры проходят проверку против публичного пакета.
6. **Протокол.** `npm run test:changes` проходит с последними исправлениями из `main` и актуальными разрешёнными путями. Синтетический цикл проверяет version/packagePath, установку, проверки приложения, идемпотентность и неуспешное обновление без потери посторонних файлов.
7. **Общая команда и CI.** `npm run verify` включает проверки слоёв, компонентов, типов, сборок, consumer, примеров документации и протокола. Проверки протокола не запускают рекурсивно настоящий worker через общий verify. CI запускает ту же команду на Node 22; заявленная минимальная версия Node соответствует реально использованным возможностям runtime.
8. **Воспроизводимость.** Установка и проверки проходят в чистом checkout итогового коммита. Ошибки сети или разрешения зависимостей расследуются; `--force` и `--legacy-peer-deps` не подменяют успешную установку.
9. **Фиксация.** Изменения закоммичены понятными этапами, итоговый `main` чист по отслеживаемым и неигнорируемым файлам. Итоговый отчёт содержит commit ID, выполненные проверки и точные ограничения проверки реального приложения.

Для заявления «реальный внешний цикл проверен» нужен отдельный успешный запуск через настоящий Codex CLI в одноразовом тестовом приложении. При недоступности среды эта проверка остаётся явно неподтверждённой; синтетические тесты не переименовываются в реальную проверку. Изменение живого приложения не требуется для чистки репозитория.

Локальный Observatory сохраняется как инструмент учёта. Если его интеграция затронута, выполняется его отдельный harness на синтетических данных; его runtime-ошибки отражаются отдельно от проверок библиотеки.

## 9. Порядок следующих этапов

После утверждения этой спецификации составляется детальный план с файлами, проверками и коммитами для следующих результатов:

1. Сохранены текущие изменения; актуальная библиотека объединена с последним протоколом без потери работы.
2. Реестр, независимый consumer и проверки отвязаны от старого каталога.
3. Новая документация стала единственной точкой входа; старый каталог и ненужные зависимости удалены.
4. Постоянные руководства, примеры и протокол согласованы с кодом; исторические документы очищены.
5. Общая проверка и CI охватывают итоговый продукт; независимая установка и проверки завершены; результат интегрирован и закоммичен.

Реализация не начинается до явного утверждения. На утверждение вынесены спецификация целиком, выбор `docs-basics` с незакоммиченными изменениями как основы актуального UI и сохранение только перехода для старого `/atomic.html`.
